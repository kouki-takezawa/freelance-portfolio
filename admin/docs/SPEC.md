# ai-company-os 仕様書

- ステータス: freelance-hp/adminを統合・移植し、本番稼働
- 更新日: 2026-08-30

## 1. 経緯

もとは2つの管理画面が別々に存在していた。

- **freelance-hp/admin**(旧): 実績・料金・お知らせ・SEO編集、お問い合わせ返信、受注・売上管理、アクセス解析。実データで稼働していた
- **ai-company-os**(旧・本リポジトリの前身): 「AIが事業部ごとに実務を下書きし、人間は承認だけ行う」という構想を先に形にしたモック版ダッシュボード。モックデータのみで、バックエンドなし

2つとも同じ「AIが実務を担当し、人間は承認フェーズだけ行う」という同じ着想だったため、実データを持つfreelance-hp/adminの機能をこのリポジトリに統合し、旧admin(別リポジトリ・別Worker)は廃止した。モック版が持っていた「3段階の自動化モデル」という考え方は、admin側に元からあった`DEPARTMENTS`(事業部・フェーズ・承認要否)の設計に統合されている(§2参照)。

## 2. 組織構成(`src/types.ts` の `DEPARTMENTS`)

トップページ(`/`。旧`/org`は`/`へリダイレクト)に表示される、AI事業部の構成。各部門は複数のフェーズを持ち、`requiresApproval: true` のフェーズだけが社長(人間)の承認を経る。各部門ボックスには実データ(件数)と、そのデータを扱う実ページへのリンクが埋め込まれている(`templates.ts`の`deptBox`/`orgChartPage`)。

| 部門 | ミッション | 実データのリンク先 |
|---|---|---|
| 経営管理部 | 全部門の進捗・課題を収集し、社長の意思決定を支援 | (トップページ自体が全社サマリー) |
| 営業部 | 問い合わせ対応〜受注獲得。最終フェーズ(送信)のみ承認必須 | `/inquiries` |
| 制作部 | HP/LP/システムの設計〜納品。最終フェーズ(納品・デプロイ)のみ承認必須 | `/orders` |
| マーケティング/SEO部 | 実績・SEO・発信内容の改善。content更新フェーズのみ承認必須 | 公開サイト(閲覧のみ、編集画面なし。§2.1参照) |
| カスタマーサクセス・保守部 | 納品後の監視・サポート・契約更新。対応実施フェーズのみ承認必須 | `/orders`(納品済み案件) |
| 総務・経理部 | 請求書・入金管理。送付・記帳フェーズのみ承認必須 | `/revenue` |

**現状の実装範囲**: 各フェーズには、実データから機械的に導出できるものに限り「実行中N件」ライブバッジを表示する(実データが存在しないフェーズには数字を捏造せず表示しない)。

| 部門 | フェーズ | 連携している実データ |
|---|---|---|
| 営業部 | 送信・フォローアップ | 未読のお問い合わせ件数 |
| 制作部 | 要件定義 / 納品・デプロイ | 見積もり中の受注件数 / 納期超過件数 |
| SNS部 | 投稿文・画像案作成 / 投稿 | SNS投稿の下書き件数 |
| 総務・経理部 | 送付・記帳 | 未入金の受注件数 |

マーケティング/SEO部・カスタマーサクセス・保守部は、フェーズ単位の実データを持たないため件数表示なし(§4.5のCron自動化が実際にcontent/blog.jsonを更新するようになれば連携可能)。

### 2.1 マーケティング/SEO部にだけ編集画面がない理由

実績・料金・お知らせ・SEO(`content/*.json`)は、もともと`/works` `/services` `/blog` `/seo`という人間が使う編集フォームを持っていたが、**運用方針として撤去した**。HPのレイアウト・内容は今後AIが自律的に判断して更新していく前提で、社長がフォームを操作することは想定していない。現状、`content/*.json`の更新はClaude CodeがGitHub Contents APIへ直接コミットする形で行う。マーケティング/SEO部のボックスには実績・料金・お知らせの件数と、公開サイトを確認するためのリンクのみを表示している。

## 2.2 content/SNSの自律更新(Cron、要 ANTHROPIC_API_KEY)

マーケティング/SEO部・SNS部AIが、実際のサービス内容と直近の投稿履歴を踏まえて新しいブログ記事案・SNS投稿案を自律的に考える仕組み(`src/ai.ts`, `runContentAutomation()`)。

- **スケジュール**: 毎週日曜21:00 UTC(月曜6:00 JST)にCloudflare Cron Triggerで実行(`wrangler.jsonc`の`triggers.crons`)
- **手動実行**: `POST /automation/run-content` でいつでも同じ処理を実行できる(動作確認・即時実行用)
- **ブログ記事**: Claudeが考えた新しい記事を、そのまま`content/blog.json`へGitHub Contents API経由でコミットする(承認フローなし。§2.1の方針どおり、AIが自律的に更新する前提)
- **SNS投稿**: 新しい下書きをKVに`status: "draft"`で保存する(投稿の実行には引き続き`/sns`での社長承認・「投稿済みにする」操作が必要。営業やSNSと違い、公開サイトへの直接反映ではないため承認フローを残している)
- **未設定時の挙動**: `ANTHROPIC_API_KEY`が未設定の場合は何も行わず、`{ ok: false, message: "..." }`を返して安全に終了する(2026-08-29時点、このキーは未設定)

## 3. データの所在

- **お問い合わせ・受注・ゴミ箱**: Cloudflare KV(`DATA`バインディング、namespace ID `e37dfd650b9a4271b2bdb5b33e364b56`)。[freelance-hp](https://github.com/kouki-takezawa/freelance-hp)公開サイトの問い合わせフォームが書き込む先と**同じKVを共有**している
- **実績・料金・お知らせ・SEO**(`content/*.json`): [freelance-hp](https://github.com/kouki-takezawa/freelance-hp)リポジトリに存在。このアプリはGitHub Contents API経由で読み書きするだけで、ファイルの所在は移動していない(公開サイト自体もfreelance-hpのまま)
- **アクセス解析**: Cloudflareアカウントの Web Analytics(GraphQL API)を直接参照。データの保存は行わない

## 2.5 パフォーマンス(ページ遷移速度)とファイル構成

- ホーム画面はGitHub Contents API(実績・料金・お知らせ)とCloudflare Analytics APIへの外部呼び出しを毎回行っており、これが体感速度に直結していた。それぞれKVに短時間キャッシュする(`cached()`ヘルパー、`src/index.ts`)。実績・料金は10分、お知らせは5分、当日PVは1分でキャッシュし、自律更新でお知らせが追加された際は該当キャッシュ(`ghcache:blog`)を即座に破棄して古い件数が残らないようにしている
- `/icon.svg` `/manifest.webmanifest` `/sw.js` はほぼ内容が変わらないため、`Cache-Control: public, max-age=86400`を付与しブラウザキャッシュを効かせている(ページ遷移のたびの再取得を防ぐ)
- `src/templates.ts`が肥大化していたため、保守性のために分割した。`src/styles.ts`(全ページ共通CSS・FOUC防止スクリプト)、`src/shell.ts`(サイドバー・コマンドパレット・AIチャットパネル・ライブ更新など画面の外枠)、`src/util.ts`(`esc`/`formatYen`など小さな共通関数)、`src/templates.ts`(各ページの中身)という構成。挙動は変えていない
- 更新系POST内で繰り返していた「操作履歴に記録しつつ件数をキャッシュ更新・配信する」処理は`afterMutation()`(`src/index.ts`)にまとめた

## 2.6 サイドバー件数のキャッシュ(KV list()のクォータ対策)

サイドバーの承認待ちバッジは元々ページを開くたびにKVの`list()`を(お問い合わせ・受注・SNS投稿の3回)実行して集計していたが、KV無料枠の`list()`は1日あたりの上限が低く、通常利用でもすぐに`KV list() limit exceeded for the day`エラーで全ページが500になる事態が発生した。そのため以下の設計に変更した。

- 件数は`summary:counts`という1件のKVキーにJSONでキャッシュし、バッジ表示だけが必要なページ(設定・アクセス解析・受注編集画面など)は`get()`1回で済ませる(`getSidebarCounts()`)
- 実データの一覧そのものが必要なページ(受注管理・お問い合わせ・SNS投稿・承認センター・ホーム)は、そのページ用に取得済みのデータからその場で正確な件数を導出し、キャッシュには依存しない
- キャッシュの更新は、更新系POSTの直後に呼ばれる`notifyCounts()`でのみ行う(閲覧だけではキャッシュを書き換えない)
- `list()`が失敗した場合(クォータ超過など)でも、`getSidebarCounts()`は0件にフォールバックし、一覧系ページは`safeList()`でエラーバナー付きの空リスト表示にフォールバックする(ページ全体を500でクラッシュさせない)

## 2.7 クライアント・検索・月次レポート・UI演出のまとめ

- **クライアント一覧・詳細**(`/clients`、`/clients/:name`): 受注の`clientName`とお問い合わせの`name`が完全一致するものを同一クライアントとみなして名寄せする(顧客IDの仕組みが無いための簡易な突き合わせ)。詳細ページは受注・お問い合わせを時系列のタイムラインで表示する
- **全データ横断検索**(`/search`): 受注・お問い合わせ・SNS投稿・アクティビティをそれぞれ最大20件まで検索する。コマンドパレットで一致するページがない状態でEnterを押すと自動的にこのページへ遷移する
- **月次経営レポート**(`/reports/monthly`): 売上・承認待ちの状況を1ページにまとめた、印刷/PDF保存向けのレイアウト(`@media print`でサイドバー等を非表示にする)
- **受注管理のマスター/ディテール**: `/orders?selected=<key>`で一覧の右側に編集フォームを表示する(`orderFormFields()`を専用ページと共通化)。一覧の行は`data-href`を持ち、クリックまたはキーボードのJ/K+Enterで開ける
- **通知センター**: サイドバー下部のベルアイコンから`GET /notifications`(直近のアクティビティ)を取得して表示する。既読管理はブラウザのlocalStorageで行う(サーバー側には既読状態を持たない)
- **組織図の演出**: AI社員の役職名をハッシュ化して色相を決めた発光オーブ(`roleAvatar()`)、実データのしきい値だけで選ぶ「AI社員の日替わりひとこと」(`aiDailyComment()`、数字を捏造しない)、部門カードのドラッグ&ドロップ並べ替え(`localStorage`の`orgOrder`に保存、KVには保存しない=閲覧者ごとの好みのため)
- **達成演出・効果音**: 承認待ちが0件になった瞬間に控えめな紙吹雪演出+効果音(Web Audio APIで合成、音声ファイルなし)。効果音は既定オフで、エラーバナー表示中(KV障害等によるフォールバックの0件)は演出しない
- **アクセントカラーパレット**: `data-palette`属性で切り替える4種類(aurora/forest/sunset/ocean)。テーマと同様に`localStorage`に保存し、FOUC防止のためブートストラップスクリプトで描画前に適用する
- 一度実装した「組織図をパン・ズーム可能なキャンバスにする」機能は、実際に使ってみて不要と判断されたため撤回した(ドラッグ&ドロップの並べ替えのみ残っている)
- 代わりに、組織図セクション(`#orgAutofit`)自体が画面の高さに収まりきらない場合だけ`transform: scale()`で自動的に縮小する(手動のズーム操作はなし)。ページ上部の見出し等を含めた全体ではなく、組織図セクション単体が画面の高さ(`window.innerHeight`)に収まるかで判定する。縮小率が0.55未満になる場合は文字が読みにくくなるため縮小せず通常のスクロールに任せる。モバイル幅(≤720px)では対象外
- ライトモードの背景色は当初やや青みがかった配色(`#f3f5fb`等)だったが、ニュートラルな薄グレー(`--bg: #eeeeee`、サイドバーの`--aside-bg`・`--surface-2`・`--border`系も同様に青みを除去)に変更した
- 一度は「時間帯によって背景にうっすら色が乗る」アンビエント演出(`data-tod`属性 + `linear-gradient`)を追加したが、光の加減によって背景に段差(バンディング)が見えてしまう不具合があったため撤去した。ライトモードの背景は`background-image: none`の完全な単色のみとし、以後この種の背景装飾は追加しない方針

## 2.8 サイドバー折り畳み・横幅統一・一覧の一括操作・アクセシビリティ

- **サイドバー折り畳み**: サイドバー上部の矢印ボタン(`#collapseBtn`)でアイコンのみの64px幅に折り畳める(`localStorage`の`sidebar-collapsed`に保存、FOUC防止のためブートストラップスクリプトで描画前に復元)。モバイル幅(≤720px)では対象外(ハンバーガーnavのため)
- **部門ごとのアコーディオン折り畳み**: サイドバーの各見出し(「AI事業部(ホーム)」「営業部」など、`NAV_SECTIONS`の各`key`)はクリックすると配下のメニュー項目だけを個別に開閉できる(`localStorage`の`nav-collapsed-sections`にカンマ区切りで保存)。現在開いているページが属する部門は、保存状態に関わらず必ず展開した状態で表示する(自分がどこにいるか見失わないため)。サイドバー自体をアイコンのみに折り畳んでいる間(上記)は、この部門ごとの開閉は無効化され、アイコンは常に全部表示される(見出し自体が見えないため開閉のしようがないのと、ナビゲーションが消えて迷子になるのを防ぐため)
- **全ページ横幅の統一**: `main.content`の`max-width`をページごとに900〜1220pxとバラバラだった状態から`1760px`に統一し、大きなモニターで右側に不自然な余白ができる問題を解消した。フォーム中心のページ(受注登録フォーム等)は`.form-narrow`(720px)で個別に狭めている
- **一覧画面の一括操作**(`/orders` `/inquiries` `/sns`): 各行にチェックボックスを追加し、1件以上選択すると一覧上部に固定(`position: sticky; top: 0`)の一括操作バーが表示される(`bulkBar()`/`bulkActionsScript()`、`src/templates.ts`)。受注は一括削除、お問い合わせは一括既読・一括削除、SNS投稿は一括投稿済み・一括削除に対応する。バックエンドは`POST /orders/bulk-delete` `POST /inquiries/bulk-read` `POST /inquiries/bulk-delete` `POST /sns/bulk-posted` `POST /sns/bulk-delete`が`{ keys: string[] }`を受け取り、既存の単体操作(`moveToTrash`/`markSnsPostPosted`等)を複数件に対して繰り返す。**注意**: Honoはルート登録順に最初にマッチしたものを採用するため、`/orders/:key`のような1セグメントの汎用パターンより前に`/orders/bulk-delete`を登録する必要がある(実際にこの順序を誤り、`bulk-delete`が`:key`側に奪われて機能しない不具合が発生したため、`src/index.ts`内でコメントを添えて順序を明示している)
- **アクセシビリティ**: コマンドパレット・キーボードショートカット一覧の各モーダルにフォーカストラップを実装(`trapFocus()`、`src/shell.ts`。Tabキーでモーダルの外にフォーカスが漏れないようにする)。ショートカット一覧には閉じるボタンを追加し、開閉時にフォーカスを適切に移動・復帰する。通知ベルは開閉に応じて`aria-expanded`を切り替える。一覧画面のJ/Kキー操作は`aria-live`領域(`#kbdLiveRegion`)へ選択中の行を読み上げる
- **ライトモードのグロー演出**: ダークモードはカード類にアクセントカラーの発光を効かせていたが、ライトモードは同じ配色だと白背景に沈んで見えたため、`.card`・`.org-box`に控えめなアクセントカラーのbox-shadowを追加した(パレット切り替えにも自動追従)
- **AI社員のひとこと欄の視覚的区別**: 「承認待ち」カードと見た目が紛らわしかったため、`.ai-comment`を左上の角だけ直角にした吹き出し風の形状・アクセントカラーの背景に変更した
- **売上グラフの空データ表示**: 入金済みデータが1件もない場合、`monthlyRevenueBarChart()`が空文字列を返して見出し下に不自然な空白ができていた。他の一覧と同じ空データデザイン(アイコン+見出し+補足)を表示するよう修正した
- **CSS Gridの子要素が縮まない不具合**: `.master-detail`(受注管理のマスター/ディテール表示)は980px未満の幅では1カラムグリッドになるが、子の`<div>`に`min-width: 0`が無いと、幅の広い`<table>`を含む場合にグリッドトラックが内容の最大幅まで広がり、ページ全体に横スクロールが生じる既知のCSS Grid挙動があった。`.master-detail > div { min-width: 0; }`で修正済み

## 4. 未実装・今後の課題

1. `ANTHROPIC_API_KEY`未設定のため、§2.2のcontent/SNS自律更新と§2.3のAIチャットパネル(PM AI)はまだ実際には動いていない(コード・UIは完成、キー投入待ち。未設定時は両方とも安全にエラーメッセージを表示するだけで、リクエストは送信されない)
2. `CF_ANALYTICS_TOKEN`未設定時はアクセス解析ページが空表示になる(既存の挙動を踏襲、致命的ではない)
3. `RESEND_API_KEY`未設定時はお問い合わせへの返信メール送信ができない(既存の挙動を踏襲)。設定待ち
4. `CONTENT_GITHUB_TOKEN`は`freelance-hp`リポジトリのみに書き込み権限を絞ったfine-grained PATを設定済み(Contents: Read and write)。有効期限が切れたら再発行が必要
5. 認証ゲートをいったん無効化しており、公開URLに誰でもアクセスできる状態(§6参照)。再度有効化する場合は`src/index.ts`のコメントアウトを戻す
6. `/automation/run-content`・`/assistant/chat`・`/live/ws`・`/notifications`は現状、認証ゲートと同じく無防備(誰でもアクセスできる)。ログインを再度有効化する際は、これらのルートも保護対象に含めること
7. `/settings`(ログインID・パスワード変更)も同様に認証ゲートの対象外だが、変更には必ず「現在のパスワード」の入力を要求しているため、パスワードを知らない第三者は変更できない(§2.4参照)

## 2.4 設定(ログインID・パスワードの変更)

`/settings`でログインID(メールアドレス)とパスワードを確認・変更できる。ログイン情報はWorkers Secretsではなく、KVの`auth:admin`キーに保存する(`src/auth.ts`の`getAdminAccount`/`setAdminAccount`)。初回アクセス時にKVへレコードがなければ、既存の`ADMIN_EMAIL`/`ADMIN_PASSWORD`シークレットから自動的に移行(シード)される。パスワードはPBKDF2(SHA-256、10万イテレーション、ランダムソルト)でハッシュ化して保存し、画面には表示しない(表示できるのはログインIDのみ)。`POST /settings/account`・`POST /settings/password`はいずれも「現在のパスワード」の一致を必須とし、一致しない場合は401を返す。

## 2.3 AIチャットパネル・承認センター・アクティビティ・リアルタイム反映

- **AIチャットパネル**: 画面右下のボタンから開ける、経営管理部「PM AI」とのチャット(`POST /assistant/chat`)。未読件数・売上などの実データのスナップショットをシステムプロンプトに含めて回答する。要 `ANTHROPIC_API_KEY`
- **承認センター**(`/approvals`): お問い合わせ・受注・SNS投稿・入金の承認待ちを1画面に集約。SNS投稿はその場で「投稿済みにする」操作ができ、他は該当ページへのリンクを表示する
- **アクティビティ**(`/activity`): 返信送信・受注更新・SNS承認・削除などの操作履歴(`src/activity.ts`、KVに90日保存)。誰が(AI社員名または「社長」)・いつ・何をしたかを記録する
- **リアルタイム反映**: `LiveRoom`という単一のDurable Object(`src/live.ts`)が全クライアントのWebSocket接続を保持し、更新系のPOSTのたびに最新の承認待ち件数をブロードキャストする。サイドバーの件数バッジはその場で更新され、一覧系のページでは「更新があります」バナーをクリックすると再読み込みする(データの差分計算までは行わない簡易的な実装)

## 6. セキュリティ上の注意(重要)

2026-08-29時点、`src/index.ts`の認証ミドルウェアはコメントアウトされており、**ログインなしで全ページ(お問い合わせの個人情報、受注・売上、ゴミ箱を含む)にアクセスできる**。公開URLを外部に共有しないこと。ログインを再度必須にする場合は、該当のコメントブロックを元に戻してデプロイし直す。
